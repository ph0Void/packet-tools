# Frontend — Packet Tools (`@packet-tools/web`)

Next.js 16 (App Router) + React 19 with React Compiler (`reactCompiler: true`), Tailwind v4, shadcn UI (`radix-nova` style) and Zustand. UI strings and comments in Spanish. Public docs in `README.md`.

## Commands and verification

| Script | Real command | Note |
| --- | --- | --- |
| `dev` | `next dev` | uses the `PORT` env (e.g. 3090) |
| `build` | `node scripts/build.mjs` | **always use this one**; forces `NODE_ENV=production` before compiling |
| `start` | `next start` | serves the build |
| `lint` | `eslint` | |

- No typecheck or test script. Verify with `npx tsc --noEmit` and `npx eslint <file>` inside `packages/web`.
- Tool-output parsers do have a runnable check, because they are pure functions without React: `npx tsx scripts/check-tooloutput.ts` (111 checks; exits 1 on failure). Versioned on purpose (`.gitignore` exception), so **when you add a backend `code` or a new field in `toolOutput.ts`, add its check there**. Besides the `configure_device` / `send_command` contract it covers approval expiry, human-readable tool titles and short errors.
- Turn ending (cancel/budget/error) plus the **real retry** have another check, for the same reason (pure logic, no React): `npx tsx scripts/check-turno-corte.ts` (94 checks). Its last block **verifies the client's durable notices match the backend's literally** (`continuation.ts`): change either copy and the check goes red.
- **Attachments** have a third: `npx tsx scripts/check-adjuntos.ts` (14 checks) over `src/component/chat/adjuntos.ts`. Without it, reusing `fileUrl` as content would break **silently** (no compile error, no warning): the backend no longer stores the file in the database.
- **STANDARD-automation commands** have a fourth: `npx tsx scripts/check-comandos-standard.ts` over `src/component/jobs/comandosStandard.ts`, mirroring `CronCommandRunner` (the three `payload` shapes, the 30-command cap, allowed protocols: SSH/Telnet/serial and SIMULATION + Packet Tracer, **not GNS3**).
- Never run bare `next build` with the root `.env` loaded (it exports `NODE_ENV=development` and breaks prerender). Detail in the root `AGENTS.md`.

## Authentication

- Two layers: `src/proxy.ts` (Next 16 convention; `proxy` function + `matcher`) only checks the `NEXT_PUBLIC_COOKIE_NAME` cookie presence for `/dashboard` and `/auth`; real validation is server-side with `getSessionUser()` from `src/action/SecureAction.ts` (`GET /api/auth/me`). The dashboard layout is `force-dynamic`.
- Login: `AuthAction.loginAction` stores the token as an httpOnly cookie (30 days) via `CookieHelper`; `SessionHydrator` hydrates it into `authStore` for UI permissions.
- There is no `src/middleware.ts`: edge logic lives in `src/proxy.ts`.

## How it talks to the backend

- Server actions: `ApiClient.api()` (`src/service/client/ApiClient.ts`) against `NEXT_PUBLIC_BACKEND_URL` with `Authorization` read from the cookie.
- Client-safe services: relative `fetch` through the `/api/:path*` rewrite in `next.config.ts`.
- Chat SSE and HITL approvals: **direct** `fetch` to the backend (no rewrite) on purpose, so the stream is never buffered. Socket.IO also direct with `withCredentials`. Do not route them through the rewrite.

## UI conventions

- shadcn in `src/components/ui/`, domain components in `src/component/`, chat pieces in `src/components/ai-elements/`. Use `cn()` from `@/lib/utils`; theme via CSS variables in `src/app/globals.css` (dark by default, `dark:` prefix).
- Use what is already installed: `lucide-react`, `sonner`, `motion` + `tw-animate-css`, `cmdk`, `radix-ui`, `class-variance-authority`. Check `package.json` before adding libraries.
- Server Components by default; `'use client'` only with interactivity. Mobile-first (`sm:`, `md:`, `lg:`).
- React Compiler is on: do not add manual `useMemo`/`useCallback` for performance alone.
- `src/components/ai-elements/prompt-input.tsx` imports `nanoid` and types from the `ai` package that are transitive (undeclared in `package.json`) dependencies; if you touch it, do not assume they are available as direct dependencies.

## State and key flows

- Zustand stores in `src/store/`: `authStore`, `chatStore` (persisted), `terminal.store` (buffer, active session, busy), `topologyStore` (persisted), `uiStore` (theme/menu).
- Chat: `ChatContext` + `src/hooks/useCiscoChat.ts` (SSE parser: `user_message`, `text_delta`, `reasoning`, `tool_call_start/result`, `tool_approval_required/resolved`, `terminal_command`, `terminal_open_requested`, `terminal_open_resolved`, `agent_progress`, `handoff`, `error`, `complete`) and `useCiscoSocket.ts`. The `error` event carries an **additive** `code` (`budget_exhausted` | `cancelled` | `agent_error`; contract in `ChatsRouter.ts` propagated via `handlers.onError(msg, code)`): on `budget_exhausted` the context stores `continuationPending` and `ChatInputComponent` shows the "Continuar tarea" button. Messages accept up to 4 attachments; `ToolCard` covers the HITL variants (`TERMINAL_REQUIRED`, approved/rejected/expired).
- **Turn ending: three, not two.** `ChatContext` exposes the turn outcome (`completo` | `cancelado` | `erroreado`) and `stop()` explicitly marks the user cut. A network failure that never opened a stream is not a turn ending and stays `completo`. With `code: "cancelled"` no error toast is shown: a cancellation is not an agent failure.
- **Partial response:** everything a turn wrote is kept as a flagged assistant message, never lost on cancel or failure. The backend appends a **durable** quote-style (`> …`) notice when persisting the cut turn and the client recognizes it there (`detectarAvisoCorte`), so the message still looks partial after reload. `src/component/chat/turnoCorte.ts` is the pure module with the whole contract; the notice is recognized by a **stable accent-less marker**, not literal equality. The notice is **not painted inside the text**: `TurnoCorteBar` renders the mark above the partial response. The mark belongs to the **message, not the segment** (a cut is about the turn; a new `kind` in `segments` would vanish from history through the `normalizarSegmentos` whitelist). A provider ref reapplies the mark when history reloads, so a cut without a persisted notice is never read as a complete answer.
- **Two buttons that never compete**: "Reintentar" (`TurnoCorteBar`, next to the partial response) relaunches **the same turn** via `POST /api/chats/:id/messages/:messageId/retry`: it reuses the already-persisted user message, runs in the same thread and duplicates neither message nor answer. The traveling id is the **user** message preceding the cut, not the assistant one shown by the bar: the backend looks it up in the table and a `local-…` id would `404`. It only appears for cancelled/error/incomplete turns; "Continuar tarea" (`ChatInputComponent`) is budget-only and also carries the plan summary and pendings (`continuationPending`).
  - `reintentarTras` still exists as a **last resort** (resends the text and spends a new turn): only when no id resolves. The three retry outcomes are handled in `ChatContext`, not the bar: `409 TURNO_EN_CURSO` → brief notice; `409 YA_REINTENTADO` → reconcile (drop local partials, do **not** add the pointed assistant message); `404` → fall back to `reintentarTras`.
  - **One turn, one lifecycle.** The open/handlers/close turn helpers in `ChatContext` are shared by send and retry: duplicating the `finally` block was the easy way for one path to close the same turn twice.
- **The composer only clears when the send went through**. The submit handler **throws when nothing was sent**: `PromptInput` clears text and attachments when `onSubmit` resolves and keeps them when it rejects. Without that, a `409 TURNO_EN_CURSO` kept the text but dropped the attachments. `maxFileSize` (10 MB) mirrors `ATTACHMENT_MAX_BYTES` so the client never uploads in base64 what the backend will reject.
- **The chat list no longer carries history**: `GET /api/chats` returns the summary with `messageCount`/`attachmentCount`, and one chat's history is fetched with `GET /api/chats/:id/messages`. Consequences: the list applier must **not** replace `store.messages` with the listing (it has no messages) and must keep each chat's already-read messages, or a refresh empties the open conversation. Keyset cursor pagination (`meta.nextCursor`, 30 chats per page, sidebar "load more"): when `meta.hasMore` is true, a chat missing from the page does **not** prove it is gone, so the active chat is never discarded. The sidebar search is local: it only scans loaded conversations.
- **Attachments: content is no longer in the database.** `Attachment.fileUrl` arrives `NULL`; the only read is `GET /api/chats/attachments/:id`, with a **relative** path (through Next's `/api/:path*` rewrite with the session cookie; composing `NEXT_PUBLIC_BACKEND_URL` into an `<img>` would pin it to the build-time URL). `src/component/chat/adjuntos.ts` is the pure module (`urlDeAdjunto`/`tieneContenidoServible`/`esImagenServible`, verified by `scripts/check-adjuntos.ts`). Thumbnails render from the endpoint and degrade to a downloadable card on `404`/`410`. **Sending is unchanged**: the data-URL still travels in `attachments[].fileUrl`; only reading changed.
- Tool output is **not rendered in `ToolCard`**: it was split. Pure parsers live in `src/component/chat/card/toolOutput.ts` and per-output-type renderers in `src/component/chat/card/toolOutputViews.tsx`. `ToolCard.tsx` only classifies and routes. Rule: **a single render point**; raw JSON only lives under "Detalles técnicos".
- **Tool cards: what NOT to do.** Four reasonable-looking things that cost performance on every stream token:
  1. **Do not read `useChatContext()` inside the card.** `ChatContext` rebuilds `streamSegments` per token, so any context consumer re-renders per token even with unchanged props and `memo` cannot help. What the card needs arrives via the `chat` prop, a memoized object: approvals, resolving, canApprove, approve/reject and console-open requests.
  2. **Do not parse output in render.** Cache by object **identity** of the `ToolExecution` in a `WeakMap`. The object is only replaced when that tool changes, so identity is a correct key. Anything depending on chat state is looked up **outside** the cache.
  3. **Do not create one `setInterval` per card.** Approval expiry goes through a module-singleton hook with **one** re-armed `setTimeout` for the nearest deadline. No pending approvals means no timer; with approvals there is exactly one (~1/min), re-rendering only cards whose text changes.
  4. **Do not repeat state or tool name.** One header with icon + readable title + **one** badge, and command blocks with an informative label, not a repetition of the badge. Errors shrink to what happened + what to do: no technical marker, no stack (that lives in "Detalles técnicos").
- Real-device configure cycle (`configure_device`) and console diagnostics (`send_command`, `read_terminal`, `wait_for_prompt`): the backend already returns `code: PLAN_ONLY | DIALOGO_PENDIENTE | NO_VERIFICADO | CONFIG_ABORTED`, `plan.lineas[]`/`plan.omitidas[]`, per-step status, pending dialog, verification and abort reasons. The card tells the story in that order and **never reports as applied what was never read back**: dry-run (info tone, no "success"), applied+verified, applied-unverified (amber), pending dialog (literal text highlighted — answer it in the terminal) and sub-mode console. State is decided by the pure tested helpers, not by `success`. Detection by payload **shape**, not `code`. Never show `sessionId`: technical data.
- `agent_progress` phases: the `AgentProgressPhase` union (`useCiscoChat.ts`) accepts `configuring`, `verifying` and `unknown`. An unknown phase is **never dropped**: warn in development and propagate it as `phase: "unknown"` with `phaseRaw`, painted as «Fase "name"». When adding a phase, extend the union, the whitelist and that map.
- **`ChatProvider` lives in `src/app/dashboard/layout.tsx`, not in pages.** Full-screen chat, global side panel and the terminal-opened chat share one state. Adding a chat page: do **not** mount it again.
- `GlobalChatPanel` is the side panel: `fixed` (never pushes content, so the layout does not shift), resizable from the left-edge handle, width persisted in `uiStore`, button in the `NavBar`. It hides itself on `/dashboard/chat` to avoid duplicating the conversation. Mounted **only while open**: mounted with `width: 0` it duplicated the whole conversation render and kept its 15 s session polling alive (`setInterval` only cleans up on unmount). Chat state lives in the `ChatProvider`, so closing loses nothing — **except the unsent composer draft**, which is local `ChatInputComponent` state (lifting it to the store is pending, not done here).
- Agentic transparency: 8 **additive** SSE events (`plan_update`, `skill_loading`, `skill_loaded`, `skill_created`, `subagent_started`, `subagent_completed`, `rag_retrieved`, `admin_action`) parsed in `useCiscoChat.ts`, stored in `ChatContext` and rendered with the `src/component/chat/items/` cards. They depend on **no flag**; the frontend only paints them when they arrive: without backend emission, chat works the same.
- Mentions: `@rag` (pre-queries the KB), `@web` (forces web search), `@skill:<slug>` (applies one skill) and `@<device>`. Autocomplete mounts **outside** `<PromptInput>` (as a sibling), opening upwards: inside it overlapped the input footer and covered the model/connection selectors and the send button.
- `normalizarSegmentos` drops unknown `kind`s: adding a new segment type means extending that whitelist or it vanishes from history. It accepts `text`, `tool` and `plan` today. **Turn cuts are NOT a `kind`**: flagged on the message, not on a segment.
- Skills: `/dashboard/skills` with `SkillsManager.tsx` + `SkillService.ts` (client-safe: relative `fetch`, **not** `ApiClient`, which imports `next/headers` and breaks the build from a client component) against `GET/POST/PUT/DELETE /api/data/skills`. Roles: create/edit need `ADMIN`/`STAFF`; delete, ADMIN only. The `@skill:<slug>` autocomplete lives in the chat items. Sidebar entry in `SideBar.tsx` (`MENU_ITEMS`, visible to all roles).
- **Automations** (`/dashboard/jobs`): the backend no longer polls every minute — it **arms an in-memory scheduler**, so the UI contract changed in three places. (1) A `STANDARD` job **executes** `payload` commands against the device: the form has a commands textarea (only with `actionType === "STANDARD"`, one per line, sent as `config: { commands: [...] }`, the alias the router serializes to `payload`) and requires **commands plus `deviceProviderId`** before saving — a topology never implies which device to command. `src/component/jobs/comandosStandard.ts` is the pure module mirroring `CronCommandRunner`, verified by `scripts/check-comandos-standard.ts`. (2) "Ejecutar Ahora" (`POST /api/jobs/:id/run`) **runs and returns the result**: never paint any "<1 min" promise. (3) `GET /api/jobs/scheduler` (ADMIN/STAFF) is how you verify an automation stayed **armed**: read with relative `fetch` (**not** `ApiClient`); the header counter and row "EN CURSO" marks come from it; on failure the indicator is simply not painted. `GET /api/jobs` user isolation is backend-enforced: the view never filters.
- Logs: `/dashboard/log`. **Isolation is backend-enforced** (`GET /api/logs` already returns only the user's own rows; ADMIN sees all, `userId = null` rows ADMIN-only), so the view never filters: it only explains it with an `Info` notice for non-admins. Dropdown levels come from `GET /api/logs/levels`, **never** a local constant: `Log.level` is a free `String`. The **Actor** column is painted by two files (header table + row items — the row renders in the child); touching a column means touching both plus the empty-state `colSpan`.
- Agent-trace switch: `AgentLogsCard.tsx` on `/dashboard/configuration` (ADMIN) against `PUT /api/config/logs`. Optimistic `Switch` (flip → action → revert on failure). Uses `revalidatePath("/dashboard/configuration")`: do **not** copy the `"/dashboard/config"` typo from the three old actions (that route does not exist).
- Layout: the anti-flash theme script goes with `next/script` + `strategy="beforeInteractive"`. A `<script dangerouslySetInnerHTML>` inside JSX is discarded by React 19 on the client (Next 16 warns).
- Terminal: xterm in `src/component/terminal/`; `USER` is read-only (`disableStdin`) and keystrokes are ignored while the agent holds the console (`terminalBusy`).
- Workspace: React Flow in `src/component/workspace/`; syncs with Packet Tracer via `emitToolCall("getNetwork")`.
- Pages in `src/app/dashboard/<route>/page.tsx` (16 routes: `alert`, `chat`, `configuration`, `connection`, `data`, `jobs`, `log`, `providers`, `resources`, `skills`, `terminal`, `topology`, `users`, `workspace`, `workspace/[id]`, plus the dashboard home); ADMIN-only ones redirect on wrong role.
- Alerts: `src/component/home/severity.ts` centralizes the severity ramp instead of raw colors per view.
- **Removed (do not resurrect)**: `src/app/dashboard/gns3/page.tsx` (the `/dashboard/gns3` route no longer exists) and `src/component/terminal/TerminalChatPanel.tsx` (replaced by `GlobalChatPanel`).
